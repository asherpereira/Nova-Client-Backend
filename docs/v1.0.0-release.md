# Nova Backend 1.0.0

Nova Backend 1.0.0 is the first release intended to be a coherent backend foundation for the Nova communications platform.

## Included

- ASP.NET Core / .NET 10 API.
- PostgreSQL persistence.
- Password hashing with ASP.NET Core Identity's password hasher.
- Short-lived JWT access tokens.
- Rotating, hashed refresh tokens.
- Device/session registration and revocation.
- Authenticated WebSocket connections at `/ws`.
- Automatic realtime message fan-out to connected conversation members.
- Idempotent client message IDs to prevent duplicate sends.
- Direct and group conversation persistence.
- Server/channel/member/role foundations.
- Presence, notifications, moderation, invites, attachments metadata, integrations, webhooks and call-session foundations.
- Device key-bundle storage for the future E2EE protocol.
- Rate limiting for authentication and message submission.
- Request-size limits and structured generic 500 responses.
- Liveness/readiness/combined health endpoints.
- Idempotent database bootstrap for fresh and existing development databases.
- Non-root production container.
- CI build, test and Docker-image validation.

## Important security boundary

Nova 1.0.0 stores message ciphertext as opaque data. It does **not** claim to provide audited end-to-end encryption. Clients must encrypt message content before sending it, and a formally designed/reviewed protocol is still required before advertising production E2EE.

Access tokens are never accepted in WebSocket query strings. WebSocket authentication uses the first JSON message:

```json
{"type":"auth","accessToken":"TOKEN"}
```

The server validates the token and verifies that its device is still active.

## Production deployment requirements

1. Set strong, unique `NOVA_DB_PASSWORD` and `NOVA_JWT_KEY` values.
2. Terminate TLS at a trusted reverse proxy and expose only HTTPS/WSS publicly.
3. Do not publish PostgreSQL directly to the internet.
4. Back up PostgreSQL and test restoration.
5. Put the service behind appropriate network-level rate limiting/WAF controls for public deployment.
6. Monitor logs and resource usage without logging passwords, tokens, private keys or message plaintext.
7. Treat the current database bootstrap as a compatibility mechanism; a versioned migration pipeline should be introduced before zero-downtime schema evolution.

## API compatibility

The stable API prefix is `/api/v1`. Clients should tolerate additive fields and unknown realtime events.

Current core endpoints:

- `GET /health`
- `GET /health/live`
- `GET /health/ready`
- `POST /api/v1/auth/register`
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/refresh`
- `POST /api/v1/auth/logout`
- `GET /api/v1/me`
- `GET /api/v1/conversations`
- `POST /api/v1/conversations`
- `GET /api/v1/conversations/{id}/messages`
- `POST /api/v1/messages`
- `GET /ws`

## What 1.0.0 deliberately does not claim

- Audited end-to-end encryption.
- Production WebRTC media transport/SFU infrastructure.
- Fully managed object storage/resumable uploads.
- Distributed multi-instance WebSocket fan-out.
- A zero-downtime database migration system.
- Account recovery/email verification.
- Abuse detection at internet scale.

Those are infrastructure/product milestones, not features that should be faked with a superficially complete API.
